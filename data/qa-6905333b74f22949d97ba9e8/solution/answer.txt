This confirmed that SimpleLogin has a session fallback mechanism. When an API request comes in without the `Authentication` header, the system checks Flask-Login's `current_user.is_authenticated`. If you're logged in via the web interface, the request succeeds with HTTP 200 and returns the normal JSON response containing the requested data. Without a valid session, you get HTTP 401 with `{"error": "Wrong api key"}`. This dual authentication approach is quite practical for developers who want to test API endpoints while logged into the dashboard, they don't need to manually set up API key headers for every request. The response body follows standard JSON format with an `error` key for failures, making it easy for clients to parse and handle authentication issues programmatically.

That same test also revealed something interesting about privileged operations. With only a browser session there is no API key, so `g.api_key` is `None` and `require_api_sudo` crashes in `check_sudo_mode_is_active(g.api_key)` on `None.sudo_mode_at`. The generic error handler in `server.py` catches that `AttributeError` and returns HTTP 500 with `{"error": "Internal error"}`, so that is the status code and the exact error message a browser-session-only request gets. The `{"error": "Need sudo"}` response with HTTP 440 is returned only when the request carries an API key without sudo mode active. That 440 status code caught my attention because it's not a standard HTTP code - it's SimpleLogin's custom status code specifically for sudo requirements. Standard HTTP doesn't define 440, so SimpleLogin chose this number to clearly distinguish sudo failures from regular authentication failures (401) or permission denials (403). This custom code allows client applications to specifically detect when sudo re-authentication is needed versus other auth issues, enabling them to prompt users to re-enter their password rather than showing a generic error.

So the raw bytes stored in Redis are pickle-serialized Python dictionaries, not JSON like I initially expected. The binary data starts with protocol bytes `[128, 4, ...]` which indicates pickle protocol 4, the most recent protocol version that Python's pickle module uses by default. This choice of pickle over JSON makes sense for Flask session storage because pickle can serialize arbitrary Python objects including datetimes and custom classes, while JSON is limited to basic types. The trade-off is that pickle data is Python-specific and not human-readable, but for server-side session storage this isn't a significant drawback.

When you deserialize an authenticated session, you find these key fields: `_user_id`, `_fresh`, `_id`, and `csrf_token`. The `_user_id` field stores the database ID of the logged-in user, which Flask-Login uses to load the user object on each request. The `_fresh` boolean indicates whether the user authenticated recently (true) or has a remembered session from a previous visit (false) - this distinction matters for security-sensitive operations. The `_id` is Flask's internal session identifier, and `csrf_token` provides cross-site request forgery protection for form submissions.

Sessions are stored with Redis keys in the format `session:{session_id}` where the session_id is a UUID v4 string. This simple prefix scheme keeps session data organized and allows for easy pattern-based operations like finding all sessions or implementing session cleanup. The session cookies are signed with `itsdangerous.Signer` using `salt='session'` and `key_derivation='hmac'`. The HMAC key derivation provides cryptographic binding between the secret key and the salt, ensuring that even if an attacker discovered signatures from a different salt context, they couldn't forge session cookies.

The session ID does NOT change during login. The `slapp` cookie value (`<session id>.<signature>`) is byte-for-byte the same before and after the successful login, and so is the Redis key `session:<session id>`. The login flow only adds `_user_id`, `_id` and `sudo_time` to the existing session, flips `_fresh` to True and extends the Redis TTL from 300 seconds to 604800 seconds (seven days); it does not create a fresh session. This means SimpleLogin doesn't implement session fixation protection through ID regeneration.

This is a notable security consideration. In a classic session fixation attack, an attacker could set a known session ID in a victim's browser before they log in, then use that same session ID to hijack the authenticated session afterward. Best practice recommends regenerating the session ID upon authentication to invalidate any pre-authentication session tokens. Looking at the codebase, `purge_session()` in `app/session.py` (line 61) does regenerate the session ID, but `grep -rn purge_session app/` shows its only caller is `logout_session()` (line 119), not the login flow. The login code (`after_login()` in `login_utils.py`) simply calls `login_user()` and sets `sudo_time`, which populates the existing session with user data without changing the session identifier. For most deployments this risk is mitigated by HTTPS and secure cookie flags, but it's worth noting that the defense-in-depth measure of session ID regeneration is not currently implemented.

Reply-To headers get replaced with a reverse alias so replies route back through SimpleLogin. This is essential for the privacy model, when someone replies to a forwarded email, their reply goes to a special reverse alias address (like `reply+uniqueid@simplelogin.co`) instead of your real email. SimpleLogin then forwards that reply to the original sender, maintaining the anonymity of your actual email address throughout the conversation.

Incoming Received headers are stripped. `forward_email_to_mailbox` in `email_handler.py` calls `delete_all_headers_except(msg, headers_to_keep)`, and `headers_to_keep` only lists From, To, Cc, Subject, Date, Message-ID, References, In-Reply-To, the SimpleLogin queue ID, List-Unsubscribe, List-Unsubscribe-Post and the MIME headers, plus Authentication-Results when the user has `include_header_email_header` enabled. Received is not in that list, so the original routing headers are not present in the forwarded message.

Custom incoming X-headers are stripped by the same call, since none of them is in `headers_to_keep`. Application-specific metadata such as tracking information or subscription IDs carried in X-headers does not reach the forwarded message.

The system also adds its own custom X-headers during forwarding: `X-SimpleLogin-Type` indicates the direction ("Forward" or "Reply"), `X-SimpleLogin-EmailLog-ID` provides a unique identifier for tracking and debugging, and `X-SimpleLogin-Envelope-From` records the original envelope sender. These headers help with troubleshooting delivery issues and provide transparency about how the message was processed.

I was curious about the alias token expiration, so I tested it against the running server with `actual_runtime_ask6_token_expiry.py`. It takes one signed suffix from `GET /api/v4/alias/options`, reads the signing time embedded in the token, and then uses that same token with `POST /api/v2/alias/custom/new` at fixed ages, really waiting in between (no clock patching and no changed `max_age`):

```python
import time
import requests
from itsdangerous.encoding import base64_decode, bytes_to_int

BASE = 'http://127.0.0.1:5080'
API_KEY = open('/tmp/sl_runtime/api_key.txt').read().strip()
client = requests.Session()
client.headers['Authentication'] = API_KEY

options = client.get(BASE + '/api/v4/alias/options').json()
suffix, signed_suffix = options['suffixes'][0]
signed_at = bytes_to_int(base64_decode(signed_suffix.rsplit('.', 2)[1]))
print(f"Signed suffix from /api/v4/alias/options: {signed_suffix}")
print(f"Embedded signing time: {signed_at} ({time.strftime('%H:%M:%S', time.gmtime(signed_at))} UTC)")
print()

for age in [0, 300, 599, 600, 601]:
    delay = signed_at + age + 0.2 - time.time()
    if delay > 0:
        time.sleep(delay)
    resp = client.post(BASE + '/api/v2/alias/custom/new', json={'alias_prefix': f'expiry{age}', 'signed_suffix': signed_suffix})
    now = time.time()
    body = resp.json()
    result = body.get('alias') or body.get('error')
    print(f"{time.strftime('%H:%M:%S', time.gmtime(now))} UTC  token age {int(now) - signed_at:>3} s  ->  HTTP {resp.status_code}  {result}")
```

```
2026-10-30 17:06:42,208 - SL - WARNING - 80 - "/app/app/api/views/new_custom_alias.py:72" - new_custom_alias_v2() -  - Alias creation time expired for <User 1 Tester tester@mailbox.test>
2026-10-30 17:06:42,209 - SL - DEBUG - 80 - "/app/server.py:284" - after_request() -  - 127.0.0.1 POST /api/v2/alias/custom/new ImmutableMultiDict([]) 412, takes 0.006643056869506836
```

The tokens expire after exactly 600 seconds, which is 10 minutes. The same token created aliases at 0, 300, 599 and 600 seconds of age and was rejected one second later, at 601 seconds, with HTTP 412 and `{"error": "Alias creation time is expired, please retry"}`. That matches `signer.unsign(signed_suffix, max_age=600)` in `app/alias_suffix.py`: the signer is an `itsdangerous.TimestampSigner`, which compares whole seconds and only raises `SignatureExpired` once the age is greater than 600.

The 10-minute window is a reasonable balance between security and usability. It's long enough that users can browse available domains, think about their alias prefix, and complete the creation process without rushing. But it's short enough to limit the window of opportunity if a signed suffix token were somehow leaked or intercepted. The `TimestampSigner` embeds the signing time directly into the token (the `.auTMSQ.` portion in the signed suffix above), so the server doesn't need to store any state to verify expiration, it simply computes whether the embedded timestamp is within the allowed age range.

The signed token format follows the pattern `{original_value}.{timestamp}.{signature}`, where the timestamp is base64-encoded and the signature is an HMAC of the value plus timestamp. This design means you can't simply modify the timestamp to extend validity because that would invalidate the signature, and you can't forge a new signature without knowing the server's secret key. The HTTP 412 (Precondition Failed) status code is an appropriate choice for this scenario since it indicates that a precondition of the request (token validity) was not met.

Every time you make an API call with a key, two database fields get updated. The `last_used` field gets set to the current timestamp via `arrow.now()`, and `times` is an integer counter that increments by 1 with each call.

The `arrow` library is used instead of Python's built-in `datetime` because Arrow provides a cleaner API and better timezone handling. The timestamp includes full ISO 8601 formatting with microsecond precision and timezone offset (e.g., `2026-01-25T14:00:45.767896+00:00`), which is useful for debugging and auditing API usage across different time zones.

These tracking fields serve multiple purposes. The `last_used` timestamp helps users identify stale API keys that haven't been used in a long time and might be candidates for revocation. It also helps with security auditing, if you suspect unauthorized access, you can check when each key was last used. The `times` counter provides a simple usage metric that can help identify unusually active keys (potential abuse) or rarely-used keys (candidates for cleanup). Both fields are updated synchronously with every API request before the actual endpoint logic runs, ensuring accurate tracking even if the endpoint itself fails. The update is committed to the database immediately via `Session.commit()`, so the stats are durably recorded.
