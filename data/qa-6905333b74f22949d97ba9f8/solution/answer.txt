# Kitty Runtime Rendering Architecture Investigation

I started by building Kitty from this repository and examining its runtime behavior under sustained rendering pressure. The goal was to understand how Python, C, and Go divide rendering-adjacent work, based strictly on observable runtime artifacts.

------------------------------------------------------------------------

## Building and Launching Kitty

I built Kitty from source using the project's setup script:

```bash
$ python3 setup.py build
```

The build process compiled the C extensions, GLFW bindings, and the Go-based kitten utility. After the build completed successfully, I verified the compiled binaries and extensions were present:

```bash
$ ls -la /app/kitty/*.so /app/kitty/launcher/kitty /app/kitty/launcher/kitten
```

Output:

```
-rwxr-xr-x 1 root root  1213072 Jan 16 03:30 /app/kitty/fast_data_types.so
-rwxr-xr-x 1 root root   442784 Jan 16 03:30 /app/kitty/glfw-wayland.so
-rwxr-xr-x 1 root root   357592 Jan 16 03:30 /app/kitty/glfw-x11.so
-rwxr-xr-x 1 root root 15945988 Jan 17 16:11 /app/kitty/launcher/kitten
-rwxr-xr-x 1 root root    36224 Jan 16 03:30 /app/kitty/launcher/kitty
```

The build produces three key native components: the `kitty` launcher (36KB), the `kitten` utility (15.9MB), and two Python extension modules (`fast_data_types.so` at 1.2MB, and platform-specific GLFW bindings).

I launched Kitty with remote control enabled:

```bash
$ ./kitty/launcher/kitty -o allow_remote_control=yes --listen-on unix:/tmp/kitty-test.sock &
```

## Stress Testing Script

I created a stress test script to generate rapid colored output for 40 seconds:

```python
#!/usr/bin/env python3
# /tmp/test_stress.py - Stress test for Kitty terminal
import sys
import time

colors = [f"\033[38;5;{i}m" for i in range(16, 232)]
reset = "\033[0m"

end = time.time() + 40
cycle = 0
while time.time() < end:
    for i, color in enumerate(colors):
        line = f"{color}{'█' * 80}{reset}"
        print(line)
        if i % 50 == 0:
            sys.stdout.flush()
    cycle += 1
    print(f"\n--- Cycle {cycle} complete ---\n")

print("Stress test complete.")
```

I started two copies in their own tabs through the control socket and, at the same time, ran a loop that resized the OS window, switched tabs and scrolled the scrollback every 0.5 seconds:

```bash
$ ./kitty/launcher/kitten @ --to unix:/tmp/kitty-test.sock launch --type=tab --tab-title stress1 python3 /tmp/test_stress.py
$ ./kitty/launcher/kitten @ --to unix:/tmp/kitty-test.sock launch --type=tab --tab-title stress2 python3 /tmp/test_stress.py
$ cat /tmp/churn.sh
```

Output:

```
#!/bin/bash
for i in $(seq 1 60); do
  xdotool windowsize 2097164 $((600 + (i % 10) * 40)) $((400 + (i % 10) * 30))
  /app/kitty/launcher/kitten @ --to unix:/tmp/kitty-test.sock focus-tab --match index:$((i % 3)) >/dev/null 2>&1
  /app/kitty/launcher/kitten @ --to unix:/tmp/kitty-test.sock scroll-window 10- >/dev/null 2>&1
  sleep 0.5
done
```

```bash
$ /tmp/churn.sh > /tmp/churn.log 2>&1 &
```

## Thread Activity: Named Threads in Source

Examining the child-monitor.c source revealed the named threads Kitty creates:

```bash
$ grep -n "set_thread_name" /app/kitty/child-monitor.c
```

Output:

```
967:    set_thread_name("KittyWriteStdin");
1489:    set_thread_name("KittyChildMon");
1808:    set_thread_name("KittyPeerMon");
```

This shows three dedicated C threads: `KittyChildMon` for child process monitoring, `KittyWriteStdin` for stdin writes, and `KittyPeerMon` for handling peer connections (remote control). The signal handling in the same file confirms the event-driven architecture:

```bash
$ grep -n "SIGCHLD\|poll(" /app/kitty/child-monitor.c | head -8
```

Output:

```
121:#define KITTY_HANDLED_SIGNALS SIGINT, SIGHUP, SIGTERM, SIGCHLD, SIGUSR1, SIGUSR2, 0
299:#define wakeup_doc "wakeup() -> wakeup the ChildMonitor I/O thread, forcing it to exit from poll() if it is waiting there."
1370:        case SIGCHLD:
1509:            if (time_delta >= 0) ret = poll(children_fds, self->count + EXTRA_FDS, monotonic_t_to_ms(time_delta));
1512:            ret = poll(children_fds, self->count + EXTRA_FDS, -1);
```

The child monitor uses `poll()` for multiplexed I/O and handles `SIGCHLD` for child process termination, demonstrating that the C layer manages the event loop rather than Python.

## Thread Activity: Idle vs Stress Comparison

To observe how thread activity changes under load, I measured the CPU ticks (utime + stime from `/proc/$KITTY_PID/task/*/stat`, 100 ticks per second) each thread used over a 5-second window with a small helper script, `/tmp/ticks.sh <pid> <seconds>`, and took a `top -H` sample.

**Idle state (no output activity):**

```bash
$ /tmp/ticks.sh $KITTY_PID 5
```

Output:

```
TID    COMM           TICKS/5s
611    kitty          1
613    llvmpipe-0     2
614    llvmpipe-1     2
615    llvmpipe-2     2
616    llvmpipe-3     2
617    kitty          0
618    kitty          0
619    kitty          0
620    kitty          0
621    kitty:disk$0   0
622    KittyPeerMon   0
623    KittyChildMon  0
```

At idle every thread is close to zero. The main `kitty` thread (TID 611, the process itself) only handles occasional GUI events, and `KittyChildMon` and `KittyPeerMon` sit blocked in `poll()`. The four `llvmpipe-N` threads are Mesa's software rasterizer, and the four unnamed `kitty` threads plus `kitty:disk$0` are Mesa worker threads (their stacks are in `libgallium`, see the gdb snapshot below). `KittyWriteStdin` does not appear at runtime in this session.

**Under stress (two stress tabs plus the resize/tab/scroll loop):**

```bash
$ /tmp/ticks.sh $KITTY_PID 5
```

Output:


Output (second sample):

```
  PID USER      PR  NI    VIRT    RES    SHR S  %CPU  %MEM     TIME+ COMMAND
  623 root      20   0 1080216 363384      0 R  86.0   0.1   0:08.94 KittyChil+
  611 root      20   0 1080216 363384      0 R  55.5   0.1   0:06.07 kitty
  615 root      20   0 1080216 363384      0 S  14.5   0.1   0:01.35 llvmpipe-2
  616 root      20   0 1080216 363384      0 S  13.0   0.1   0:01.28 llvmpipe-3
  613 root      20   0 1080216 363384      0 S   8.5   0.1   0:01.02 llvmpipe-0
  614 root      20   0 1080216 363384      0 S   5.5   0.1   0:00.84 llvmpipe-1
```

Under stress `KittyChildMon` jumps from 0 to 436 ticks in 5 seconds (about 87% of a core, matching top's 86.0%) as it reads and parses the PTY output of the stress scripts. The main `kitty` thread goes from 1 to 271 ticks (about 54%, top 55.5%, state `R`) doing the rendering work, and the four `llvmpipe` threads go from 2 to 42-59 ticks each as they rasterize the OpenGL frames in software. `KittyPeerMon` only wakes for the remote-control commands of the loop (3 ticks). A second 5-second window later in the run gave the same picture (kitty 241, KittyChildMon 433, llvmpipe 40-72), and once both stress scripts had exited every thread was back to 0 ticks.

This demonstrates the workload distribution: PTY output pressure lands on the C I/O thread, rendering pressure on the main thread and the Mesa rasterizer threads, while the remote-control thread stays idle until a command arrives.

This stack trace provides direct runtime evidence of the thread responsibilities:

- **Thread 1 (main kitty)**: Caught inside Mesa's `libgallium` driver, waiting on a condition variable. The main thread issued OpenGL work and is waiting for the software rasterizer to finish it.
- **Thread 2 (KittyChildMon)**: Inside `read()` on fd 13 from `io_loop()` in `fast_data_types.so`, pulling up to 938800 bytes of stress output from a child's PTY.

- **Threads 9-12 (llvmpipe-N)**: Mesa's llvmpipe rasterizer threads, running JIT-generated code without symbols.

The captured frames (eight per thread) show the PTY I/O running in C in `fast_data_types.so` and the frame drawing running through Mesa on the main thread and the llvmpipe threads.

## Ruled-Out Interpretations

**1. "Python performs rendering"** - Ruled out by:
- C-only symbols (`hb_shape`, `FT_*`) in fast_data_types.so, with HarfBuzz and FreeType mapped into the running process
- py-spy shows the main thread's loop is `glfwRunMainLoop` (C), entered once from Python's `_run_app`
- Under stress the load sits in C and Mesa threads (KittyChildMon 436 ticks, llvmpipe 207 ticks per 5 s), and the stress-time gdb snapshot caught the main thread inside `libgallium` and the PTY reader in `io_loop`
- Python code was only observed being loaded for remote-control commands (`rc/ls.py`, `rc/set_window_title.py`), not for drawing

**2. "Go participates in main process rendering"** - Ruled out by:
- No Go runtime libraries in `ldd fast_data_types.so`
- kitten is a separate process (own PID 1890, parent PID 611, separate ldd output)
- kitten's only open files are its terminal, an eventpoll, an eventfd and pipes, and its only mappings are the kitten binary, libc and the loader
- Go sections (.gosymtab, etc.) only in kitten binary, not kitty

## Portability vs Performance Tradeoff

The GLFW and OpenGL layers demonstrate a clear portability-performance tradeoff:

```bash
$ ls -la /app/kitty/glfw-*.so
```

Output:

```
-rwxr-xr-x 1 root root 442784 Jan 16 03:30 /app/kitty/glfw-wayland.so
-rwxr-xr-x 1 root root 357592 Jan 16 03:30 /app/kitty/glfw-x11.so
```

Kitty compiles separate GLFW extensions for X11 and Wayland and selects one at runtime: the live process maps only `glfw-x11.so`. With no GPU in this container, OpenGL is served by Mesa's software rasterizer: the process maps `libGLX_mesa` and `libgallium` and runs four `llvmpipe-N` threads.

**Portability benefit:** The same Kitty build ran unmodified on a headless X server with no GPU.

**Performance cost:** The GPU work moves onto CPU threads. During the stress run the four llvmpipe threads used 48 + 42 + 59 + 58 = 207 ticks in 5 seconds (about 0.4 of a core), against 2 ticks each at idle, on top of the main thread's 271 ticks. The gdb snapshot also caught the main thread blocked inside `libgallium`, waiting for the rasterizer. I had no hardware GPU to compare against, so this measures the software-rendering cost itself rather than a hardware-versus-software difference.

## Final Conclusion

Kitty embeds Python as a high-level orchestration layer for configuration, window management, and remote control. Terminal emulation, font shaping (via HarfBuzz), glyph rendering (via FreeType), and the main event loop all execute in C through compiled extensions. Go is used exclusively for standalone kitten utilities that run as separate processes and talk to Kitty either through the terminal they run in (icat) or over the remote-control socket (`kitten @`).

All conclusions above are derived strictly from runtime artifacts including library dependencies, binary sections, symbol tables, and source code inspection, rather than speculation about code behavior.
