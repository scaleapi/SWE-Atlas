I worked with the Paperless-NGX checkout in `/app` as it is (version 1.7.0 in `src/paperless/version.py`), without modifying any source files. At this commit Paperless-NGX does not use Celery: background work runs on django-q with Redis as the broker, the consumption directory is watched by the `document_consumer` management command, and the default database is SQLite at `/app/data/db.sqlite3`. I ran every service directly from `/app/src` with debug logging enabled (`PAPERLESS_DEBUG=true`).

```bash
cd /app/src
mkdir -p ../consume ../media ../data
redis-server --daemonize yes
python3 manage.py migrate
gunicorn -c ../gunicorn.conf.py paperless.asgi:application > /tmp/gunicorn.log 2>&1 &
```

No additional tasks show up for parsing, classification or indexing: the qcluster processed exactly one task, `[test_document.txt]`, and `LLEN django_q:paperless:q` returned 0 afterwards. All stages run inside that single `consume_file` task. `Consumer.try_consume_file` in `src/documents/consumer.py` detects the MIME type, selects and runs the parser (the parsing stage), generates the thumbnail, loads the classifier (the classification stage, which here reports that no model exists yet) and saves the record. It then sends the `document_consumption_finished` signal, whose handlers are connected in `src/documents/apps.py`: `add_inbox_tags`, `set_correspondent`, `set_document_type`, `set_tags`, `set_log_entry` and `add_to_index`. The last one writes the document into the Whoosh full-text index (the indexing stage), still within the same task.

With that behavior in mind, I traced the code path. The part of the system that detects new files is the `document_consumer` management command in `src/documents/management/commands/document_consumer.py`. `Command.handle` first calls `_consume()` for every file already in the directory, then watches it. With inotify available and `PAPERLESS_CONSUMER_POLLING` at 0 it runs `handle_inotify`, which logs "Using inotify to watch directory for changes", waits for `CLOSE_WRITE`/`MOVED_TO` events and calls `_consume(filepath)` once a file has been quiet for 0.5 s. Otherwise `handle_polling` uses a watchdog `PollingObserver` whose `Handler.on_created`/`on_moved` call `_consume_wait_unmodified`, which calls `_consume`.

`_consume()` in the same file is the component that creates the ingestion task object. It skips directories, ignored and unsupported files, checks that the file can be opened, optionally derives tag ids from sub-directories, and then calls:

```python
logger.info(f"Adding {filepath} to the task queue.")
async_task(
    "documents.tasks.consume_file",
    filepath,
    override_tag_ids=tag_ids if tag_ids else None,
    task_name=os.path.basename(filepath)[:100],
)
```

`async_task` comes from `django_q.tasks` (django-q 1.3.9 is installed). It builds the task dict seen in the broker (id, name, func, args, kwargs, started), packs it with `SignedPackage.dumps` and pushes it with the Redis broker's `enqueue` (`RPUSH` onto `django_q:paperless:q`). The broker connection comes from `Q_CLUSTER` in `src/paperless/settings.py` (`"name": "paperless"`, `"redis": os.getenv("PAPERLESS_REDIS", "redis://localhost:6379")`). The queuing framework that dispatches the task is therefore django-q on Redis. The `qcluster` process pulls the entry, runs `documents.tasks.consume_file(path, override_tag_ids=None)`, which calls `Consumer().try_consume_file(...)`, and stores the outcome in `django_q_task`. The same cluster also runs the periodic schedules registered by migration `1001_auto_20201109_1636` (classifier training and index optimization).

When I was done I stopped the gunicorn, consumer and qcluster processes and the Redis server, and removed the temporary `/app/consume`, `/app/media` and `/app/data` directories, so the test file, the stored document, the SQLite database and the index were all deleted and the repository was left unchanged.
