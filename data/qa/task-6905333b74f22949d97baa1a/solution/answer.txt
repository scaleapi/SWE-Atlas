I started by exploring the MinIO repository to understand how to set up a local development server. The repository contains a pre-built `minio` binary (version DEVELOPMENT.2024-11-25T17-10-22Z, built from this commit), which made getting started straightforward - no compilation needed. I wanted to see exactly what happens when you run MinIO for the first time and use it for basic S3 operations.

My approach was to perform a complete "first bucket" workflow: start the server, create a bucket, upload multiple objects, list them, download one, and verify everything persists after a restart. Along the way, I captured HTTP requests/responses with `curl -v` (signing requests with curl's built-in `--aws-sigv4` support), server-side request logs with `mc admin trace`, and filesystem artifacts to understand how MinIO processes requests internally.

Think of MinIO as a lightweight, self-contained file server that speaks the same "language" (S3 API) as Amazon's cloud storage. Instead of storing files in a complex database, it uses your local filesystem with a metadata structure that enables features like versioning and distributed storage.

To start the server, I ran:

```bash
cd /app && MINIO_CI_CD=on MINIO_ROOT_USER=minioadmin MINIO_ROOT_PASSWORD=minioadmin ./minio server /tmp/minio-data --console-address ":9001"
```

The startup output immediately tells you everything you need to know about the running instance:

```text

```

MinIO separates its S3-compatible API (port 9000) from its web management console (port 9001). This is a nice design choice - you can expose only the API to applications while keeping the admin console on a different network if needed. The warning about default credentials is a helpful security reminder that you'd want to address before any production deployment.

To understand what's happening on the server side during operations, I configured the `mc` client (`mc alias set local http://127.0.0.1:9000 minioadmin minioadmin`) and ran `mc admin trace local` and `mc admin trace -v local` in the background, writing to two log files. The trace shows every request as it arrives, how long each operation takes, and how much data flows in each direction.

To understand how MinIO actually stores data, I examined the filesystem:

```bash
find /tmp/minio-data -type f | sort
ls -l /tmp/minio-data/my-first-bucket/*/xl.meta
```

```text
/tmp/minio-data/.minio.sys/buckets/my-first-bucket/.metadata.bin/xl.meta
/tmp/minio-data/.minio.sys/config/config.json/xl.meta
/tmp/minio-data/.minio.sys/config/iam/format.json/xl.meta
/tmp/minio-data/.minio.sys/format.json
/tmp/minio-data/.minio.sys/pool.bin/xl.meta
/tmp/minio-data/my-first-bucket/data.json/xl.meta
/tmp/minio-data/my-first-bucket/hello.txt/xl.meta
-rw-r--r--    1 root     root           569 Nov  3 01:24 /tmp/minio-data/my-first-bucket/data.json/xl.meta
-rw-r--r--    1 root     root           453 Nov  3 01:24 /tmp/minio-data/my-first-bucket/hello.txt/xl.meta
```

The storage layout has two parts: `.minio.sys/` holds system metadata (`format.json`, the pool and server configuration, IAM format, and per-bucket metadata in `.minio.sys/buckets/my-first-bucket/.metadata.bin/xl.meta`), and `my-first-bucket/` is the user bucket directory. Each object becomes a directory containing an `xl.meta` file (453 bytes for hello.txt, 569 bytes for data.json) rather than being stored as a plain file. This design supports MinIO's features like versioning and erasure coding.

This answers the question about how the system processes requests and persists data: when MinIO receives a PUT request, it creates a directory for the object (e.g., `/tmp/minio-data/my-first-bucket/hello.txt/`) and writes an `xl.meta` file containing both metadata and, for small objects, the object content. As soon as the `xl.meta` file is written, the data is on disk.

Checking the format.json file:

```bash
cat /tmp/minio-data/.minio.sys/format.json
```

```json
{"version":"1","format":"xl-single","id":"be7514e2-0d6c-4f4c-bd52-a62e8ad98528","xl":{"version":"3","this":"5e9468d8-6152-4a6a-bca2-83c61cc6bf5d","sets":[["5e9468d8-6152-4a6a-bca2-83c61cc6bf5d"]],"distributionAlgo":"SIPMOD+PARITY"}}
```

This confirms a single-node setup with the "xl-single" format. The distribution algorithm "SIPMOD+PARITY" indicates how objects would be distributed across erasure sets in a multi-drive setup.

So what did all of this tell me about how MinIO works?

In terms of HTTP status codes, MinIO uses standard HTTP semantics: 200 OK for successful operations (bucket created, object uploaded/downloaded, list completed), 403 Forbidden for authentication failures (invalid credentials or missing auth), and 409 Conflict for resource conflicts (bucket already exists).

For response headers, there are some key ones to watch for: `Server: MinIO` identifies the server, `X-Amz-Request-Id` provides a unique request identifier for tracing (e.g., `18E46486F432C529`), `ETag` contains the MD5 hash of object content (e.g., `"a2bc185bfea4f26d3bfeaf1b41948564"`), `Location` is returned on bucket creation, and `X-Ratelimit-Limit` shows the rate limit ceiling (value varies by environment).

The server-side logging through `mc admin trace` provides excellent visibility. The condensed format is:

```text
TIMESTAMP [STATUS] OPERATION ENDPOINT/PATH CLIENT_IP DURATION ⇣ TTFB ↑ REQUEST-BYTES ↓ RESPONSE-BYTES
```

The entries I saw were `s3.PutBucket` for bucket creation, `s3.PutObject` for object writes (the data write operations), `s3.ListObjectsV2` for the listing, `s3.GetObject` for the read, and `s3.ListObjectsV1` with `[403 Forbidden]` for the failed authentication attempts. The verbose mode (`mc admin trace -v`) adds the full request and response headers between `[REQUEST ...]` and `[RESPONSE]` markers, which show the HTTP method, path, client IP and headers of each request.

On the authentication side, MinIO requires AWS Signature Version 4 authentication with access key/secret key credentials (default: `minioadmin/minioadmin`). Simple username/password authentication won't work - you need properly signed requests, which `curl --aws-sigv4`, the `mc` client or AWS SDKs produce.

As for data storage, everything is stored directly on the filesystem at the configured data path (`/tmp/minio-data/`), not in a database: each bucket becomes a directory, each object becomes a subdirectory containing an `xl.meta` file, small objects are stored inline within the metadata, and the directory-per-object structure supports features like versioning. Data survives server restarts because the server simply reads its state from the filesystem on startup.

For someone onboarding to this codebase, the most important insight is that MinIO gives you the familiar S3 API while keeping everything local and inspectable: you can see exactly where your data lives and watch every request with `mc admin trace`.

Throughout this investigation, I did not modify any repository source files. I used curl commands and the mc client to interact with the server, and when done I stopped the server and removed /tmp/minio-data and the temporary test files in /tmp/a1a.
