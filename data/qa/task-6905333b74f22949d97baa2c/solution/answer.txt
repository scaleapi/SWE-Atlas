I started digging into how SFTPGo handles external utilities like rsync, and pretty quickly found myself looking at the parseCommandPayload function in sftpd/ssh_cmd.go. What caught my attention was how simple the parsing logic is, it just uses strings.Split on spaces. I wanted to see what this actually means in practice, so I wrote a quick test:

```bash
cat > /tmp/test_parsing.go << 'EOF'
package main

import (
    "fmt"
    "path"
    "path/filepath"
    "strings"
)

func parseCommandPayload(command string) (string, []string, error) {
    parts := strings.Split(command, " ")
    if len(parts) < 2 {
        return parts[0], []string{}, nil
    }
    return parts[0], parts[1:], nil
}

// getDestPath is the verbatim body of (*sshCommand).getDestPath from
// sftpd/ssh_cmd.go, lifted to run on the args slice directly so this
// standalone program exercises the real destination-path logic.
func getDestPath(args []string) string {
    if len(args) == 0 {
        return ""
    }
    destPath := strings.Trim(args[len(args)-1], "'")
    destPath = strings.Trim(destPath, "\"")
    destPath = filepath.ToSlash(destPath)
    if !path.IsAbs(destPath) {
        destPath = "/" + destPath
    }
    result := path.Clean(destPath)
    if strings.HasSuffix(destPath, "/") && !strings.HasSuffix(result, "/") {
        result += "/"
    }
    return result
}

func main() {
    testCases := []string{
        "rsync --server -e.Lsfx . /uploads",
        "rsync --server --rsync-path=/bin/sh . /uploads",
        "rsync --server . '/uploads/my file.txt'",
    }
    for _, cmd := range testCases {
        name, args, _ := parseCommandPayload(cmd)
        destPath := getDestPath(args)
        fmt.Printf("Input: %s\n", cmd)
        fmt.Printf("  Name: %s, Args: %v, DestPath: %s\n\n", name, args, destPath)
    }
}
EOF
go run /tmp/test_parsing.go
```

Output:
Input: rsync --server -e.Lsfx . /uploads
  Name: rsync, Args: [--server -e.Lsfx . /uploads], DestPath: /uploads

Input: rsync --server --rsync-path=/bin/sh . /uploads
  Name: rsync, Args: [--server --rsync-path=/bin/sh . /uploads], DestPath: /uploads

Input: rsync --server . '/uploads/my file.txt'
  Name: rsync, Args: [--server . '/uploads/my file.txt'], DestPath: /file.txt

That second test case is interesting . the "--rsync-path=/bin/sh" flag just gets passed through as a regular argument. There's no filtering happening here at all. The function splits on spaces and that's it. Whatever arguments the client sends become part of the args slice.

Before diving into what happens downstream, I should clarify where filtering actually does occur. Looking at processSSHCommand in ssh_cmd.go, the command name (like "rsync" or "scp") gets checked against an allowlist using utils.IsStringInSlice(name, enabledSSHCommands). The allowlist is defined in sftpd.go:

```bash
cat > /tmp/test_allowlist.go << 'EOF'
```

So the filtering rule is simple: only the command name gets validated against a whitelist. Commands like "ls", "cat", "rm", or "bash" would be rejected. But here's the critical gap: once a command passes the name check, none of its arguments get filtered. The allowlist only gates which executables can run, not what flags they receive.

This got me wondering about what happens to these arguments downstream. Looking at getSystemCommand in ssh_cmd.go, I can see the flow as the command gets parsed, then the last argument (the destination path) gets validated through ResolvePath. But everything else? It just passes straight through to exec.Command. So I tested what this means for dangerous flags:

```bash
cat > /tmp/test_dangerous_flags.go << 'EOF'
```

The quote handling is also broken in an interesting way. Since it's just splitting on spaces, quoted strings don't stay together.

What really matters is the order of operations. To ground this, here is the real getSystemCommand method, copied verbatim from /app/sftpd/ssh_cmd.go, which is what actually assembles and runs the command:

```go
func (c *sshCommand) getSystemCommand() (systemCommand, error) {
	command := systemCommand{
		cmd:      nil,
		realPath: "",
	}
	args := make([]string, len(c.args))
	copy(args, c.args)
	var path string
	if len(c.args) > 0 {
		var err error
		sshPath := c.getDestPath()
		path, err = c.connection.fs.ResolvePath(sshPath)
		if err != nil {
			return command, err
		}
		args = args[:len(args)-1]
		args = append(args, path)
	}
	if c.command == "rsync" {
		// we cannot avoid that rsync create symlinks so if the user has the permission
		// to create symlinks we add the option --safe-links to the received rsync command if
		// it is not already set. This should prevent to create symlinks that point outside
		// the home dir.
		// If the user cannot create symlinks we add the option --munge-links, if it is not
		// already set. This should make symlinks unusable (but manually recoverable)
		if c.connection.User.HasPerm(dataprovider.PermCreateSymlinks, c.getDestPath()) {
			if !utils.IsStringInSlice("--safe-links", args) {
				args = append([]string{"--safe-links"}, args...)
			}
		} else {
			if !utils.IsStringInSlice("--munge-links", args) {
				args = append([]string{"--munge-links"}, args...)
			}
		}
	}
	c.connection.Log(logger.LevelDebug, logSenderSSH, "new system command %#v, with args: %v path: %v", c.command, args, path)
	cmd := exec.Command(c.command, args...)
	// ... wrapCmd / uid / gid setup, then:
	return command, nil
}
```

The real code copies the full argument slice produced by parseCommandPayload, derives the destination with getDestPath, resolves only that single last argument through ResolvePath, swaps it back into place, and then hands the whole slice, with every other flag left untouched, to exec.Command. To make that ordering concrete I wrote an illustrative model that walks through those same steps. This is a hand-written trace of the ordering, not the server's own code path, and its ResolvePath line is a simplified stand-in for the real vfs ResolvePath:

This trace mirrors the real getSystemCommand above: the injected flag is already sitting in the args slice before ResolvePath ever runs, and ResolvePath only validates the final destination argument, never the flags in between. The permission and path checks operate on the resolved path, not on what flags are being passed, so by the time exec.Command(c.command, args...) is reached the malicious flag is already part of the command line and cannot be stripped out.

I also looked at the symlink protections. The server tries to add --safe-links or --munge-links to prevent symlink-based escapes, but there's a problem with how it checks if the flag is already present:

```bash
cat > /tmp/test_symlink_check.go << 'EOF'
package main

import "fmt"

func IsStringInSlice(obj string, list []string) bool {
    for _, v := range list {
        if v == obj {
            return true
        }
    }
    return false
}

func injectSymlinkFlags(args []string) []string {
    result := make([]string, len(args))
    copy(result, args)
    if !IsStringInSlice("--safe-links", result) {
        result = append([]string{"--safe-links"}, result...)
    }
    return result
}

func main() {
    testCases := [][]string{
        {"--server", ".", "/uploads"},
        {"--server", "--safe-links", ".", "/uploads"},
        {"--server", "--safe-links=0", ".", "/uploads"},
    }

    for _, args := range testCases {
        found := IsStringInSlice("--safe-links", args)
        result := injectSymlinkFlags(args)
        fmt.Printf("Args: %v\n", args)
        fmt.Printf("  Exact match '--safe-links': %v\n", found)
        fmt.Printf("  After injection: %v\n\n", result)
    }
}
EOF
go run /tmp/test_symlink_check.go
```

Output:
Args: [--server . /uploads]
  Exact match '--safe-links': false
  After injection: [--safe-links --server . /uploads]

Args: [--server --safe-links . /uploads]
  Exact match '--safe-links': true
  After injection: [--server --safe-links . /uploads]

See that last case, if you send --safe-links=0, the exact string match for "--safe-links" fails, so the server adds "--safe-links" to the beginning. But now rsync sees both flags, and depending on how rsync handles duplicates, the --safe-links=0 might take precedence and disable the protection entirely.

There's also an issue with the path containment check. When a resolved path is validated against the user's home directory, ResolvePath in vfs/osfs.go calls isSubDir. Here is the real function, copied verbatim from /app/vfs/osfs.go:

```go
func (fs *OsFs) isSubDir(sub, rootPath string) error {
	// rootPath must exist and it is already a validated absolute path
	parent, err := filepath.EvalSymlinks(rootPath)
	if err != nil {
		fsLog(fs, logger.LevelWarn, "invalid home dir %#v: %v", rootPath, err)
		return err
	}
	if !strings.HasPrefix(sub, parent) {
		err = fmt.Errorf("path %#v is not inside: %#v", sub, parent)
		fsLog(fs, logger.LevelWarn, "error: %v ", err)
		return err
	}
	return nil
}
```

So the containment test is a single `strings.HasPrefix(sub, parent)` with no trailing-separator guard. I isolated that exact primitive on the candidate paths to observe how it behaves:

```bash
cat > /tmp/test_hasprefix.go << 'EOF'
package main

import (
    "fmt"
    "strings"
)

func main() {
    // The containment test inside (*OsFs).isSubDir is exactly:
    //     if !strings.HasPrefix(sub, parent) { ... return error }
    tests := []struct {
        parent string
        sub    string
    }{
        {"/home/user", "/home/user/uploads"},
        {"/home/user", "/home/user_attacker"},
        {"/home/user", "/home/user2"},
    }
    for _, t := range tests {
        fmt.Printf("strings.HasPrefix(%q, %q) = %v\n", t.sub, t.parent, strings.HasPrefix(t.sub, t.parent))
    }
}
EOF
go run /tmp/test_hasprefix.go
```

Output:
strings.HasPrefix("/home/user/uploads", "/home/user") = true
strings.HasPrefix("/home/user_attacker", "/home/user") = true
strings.HasPrefix("/home/user2", "/home/user") = true

Because the real check is a bare prefix comparison, /home/user_attacker is treated as being inside /home/user even though it is a sibling, not a child. Without appending a path separator to parent before the prefix test, any home directory whose path is a string prefix of another user's home can slip past containment. That's a classic prefix-matching path-containment weakness.

Putting this all together, the security model has some serious holes. The command name gets checked against an allowlist, and the final path argument goes through ResolvePath, but everything in between , all those flags and intermediate arguments , just passes straight through to exec.Command with no validation. The parseCommandPayload function uses basic string splitting, quotes aren't handled as grouping delimiters, and the symlink protections can be bypassed with flag value tricks. The whole thing adds up to CVE-2025-24366, which lets attackers inject arbitrary rsync flags including --rsync-path for command execution.
