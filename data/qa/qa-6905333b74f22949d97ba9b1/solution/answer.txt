Services That Stay Disabled or Skipped

These subsystems are inactive on a default start specifically because nothing configures them; Grafana falls back to a built-in default or leaves the feature off instead of failing:

| Subsystem | What the run shows | Default in `conf/defaults.ini` | What turns it on |
|-----------|--------------------|--------------------------------|------------------|
| SMTP / email | no startup message; emails cannot be sent | `[smtp] enabled = false`, `host = localhost:25` | `[smtp] enabled = true` plus a reachable `host` |
| Image renderer | `Failed to get renderer plugin sources` on first start; `rendererAvailable: False` | `[rendering] server_url =` (empty), no renderer plugin installed | install the `grafana-image-renderer` plugin or set `server_url` to a remote renderer |
| Remote cache | no Redis/Memcached connection | `[remote_cache] type = database` | `type = redis` or `memcached` with a connection string |
| Anonymous auth | `anonymousEnabled: False`; anonymous requests get 401 | `[auth.anonymous] enabled = false` | `[auth.anonymous] enabled = true` |
| LDAP / auth proxy / OAuth | `ldapEnabled: False`, `authProxyEnabled: False` | `enabled = false` in each section | enable and configure the provider |
| External plugins | `Failed to load external plugins` on the first start only | `plugins = data/plugins` (directory does not exist yet) | goes away once `data/plugins` exists |

The relevant config sections:

```
$ grep -n -A3 "^\[smtp\]\|^\[auth.anonymous\]\|^\[remote_cache\]\|^\[rendering\]\|^\[database\]" conf/defaults.ini | head -60

...
188:[remote_cache]

This is why some subsystems "claim success" and others look disabled or skipped: everything that needs only local resources (SQLite store, migrations, built-in plugins, alerting scheduler, HTTP server) starts, while everything that depends on external infrastructure or an opt-in setting (mail server, renderer, Redis/Memcached, anonymous or external auth) stays off until it is explicitly configured. The `error`-level renderer and external-plugin lines on the first start are not fatal; they only mean `data/plugins` was missing at that moment.

| Aspect | First run | Second run |
|--------|-----------|------------|
| Database file | `Creating SQLite database file` | no creation message, existing file reused |
| Migrations | `performed=626 skipped=0 duration=359.946737ms` | `performed=0 skipped=626 duration=608.028µs` |
| Default admin / org | `Created default admin`, `Created default organization` | no message, still exactly 1 user |
| External plugins | load fails (`data/plugins` missing), 54 plugins | lokiexplore-app registered from disk, 55 plugins |
| Background download | lokiexplore-app downloaded from grafana.com | nothing to install |
| Renderer lookup | error, plugins path missing | no error (still no renderer, so still unavailable) |

Why the behaviour differs, from the code:

- Migrations are tracked: the migrator reads the `migration_log` table (`GetMigrationLog()` in `pkg/services/sqlstore/migrator/migrator.go`) and only runs migrations whose id is not recorded there, then logs `migrations completed performed=… skipped=…`. On the second run all 626 ids are already recorded, so all are skipped.
- Admin creation is skipped once users exist: `ensureMainOrgAndAdminUser()` in `pkg/services/sqlstore/sqlstore.go` runs `SELECT COUNT(id) AS Count FROM "user"` and returns early when the count is above 0; only otherwise (and only if `disable_initial_admin_creation` is false) does it create the admin from `[security] admin_user`/`admin_password`/`admin_email` and log `Created default admin`. Changing `admin_password` in the config after the first run therefore has no effect on the existing account.
- The preinstalled plugin is already on disk under `data/plugins/`, so the background installer has nothing to do.

All of this state lives in `data/`, so deleting that directory is what returns Grafana to the first-run behaviour. If grafana.com cannot be reached, the background installer logs `Failed to install plugin` for grafana-lokiexplore-app and tries again on every start until the download succeeds.

$ curl -s -u admin:admin http://localhost:3000/api/datasources

```

There are three sources:

1. Core plugins shipped with Grafana (`signature: internal`). Their frontends live in `public/app/plugins/` (`public/app/plugins/datasource/` and `public/app/plugins/panel/`) and are built into `public/build`. The data sources with a Go backend are compiled into the `grafana` binary and registered in `pkg/plugins/backendplugin/coreplugin/registry.go`: `cloudwatch`, `stackdriver` (Cloud Monitoring), `grafana-azure-monitor-datasource`, `elasticsearch`, `graphite`, `influxdb`, `loki`, `opentsdb`, `prometheus`, `tempo`, `grafana-testdata-datasource`, `grafana-postgresql-datasource`, `mysql`, `mssql`, `grafana-pyroscope-datasource`, `parca` and `zipkin` (plus the internal `grafana` data source). Panels such as `timeseries`, `table`, `stat`, `gauge` and `geomap` are frontend-only core plugins.
2. External plugins loaded from disk at runtime from `data/plugins/` (the `plugins` path). On a fresh install that directory starts empty.
3. Plugins fetched from grafana.com: `grafana-lokiexplore-app` is the only non-core plugin (`?core=0` returns just it, signed by grafana). Nobody installed it explicitly; it is hard-coded as a default preinstalled plugin:

```
$ grep -n "lokiexplore\|preinstall" pkg/setting/setting_plugins.go | head -20
31:		// Default preinstalled plugins
32:		"grafana-lokiexplore-app": {"grafana-lokiexplore-app", "", ""},
49:	disablePreinstall := pluginsSection.Key("preinstall_disabled").MustBool(false)
...
79:		cfg.PreinstallPluginsAsync = pluginsSection.Key("preinstall_async").MustBool(true)
```

With `preinstall_async = true` it is installed in the background after the server is already listening, which is why it is missing from the first `Plugins loaded count=54` and present on the next start (`count=55`). Setting `[plugins] preinstall_disabled = true` stops this.

Plugins being available is not the same as data sources being configured: `/api/datasources` returns `[]`. Every data source type is available, but no data source instance exists until one is added in the UI, through the API or by provisioning files.

Generated Files Required Before the Server Runs

```
$ ls -la pkg/server/wire_gen.go; head -8 pkg/server/wire_gen.go; git check-ignore -v pkg/server/wire_gen.go; git ls-files pkg/server/wire_gen.go | wc -l

.gitignore:194:**/wire_gen.go	pkg/server/wire_gen.go

```

Wire generates `pkg/server/wire_gen.go`, the dependency-injection code that constructs every service from `pkg/server/wire.go`. It is git-ignored and not committed, so a fresh clone does not have it: it must be generated before the server can compile and run. `make gen-go` runs Wire on `./pkg/server`, and `make build-go` depends on `gen-go`. In this checkout the file was already generated when `bin/grafana` was built, so running `./bin/grafana server` directly and building first behave the same. Starting from a clean clone with `go run ./pkg/cmd/grafana server` without generating first fails to compile. The frontend works the same way: the UI is served from the compiled `public/build` bundle, so the frontend has to be built before the UI loads.

Summary

On a completely clean start, Grafana:

1. Uses only `conf/defaults.ini`, with home `/app` and data, logs and plugins under `data/`.
2. Creates a SQLite3 database at `data/grafana.db` and runs 626 migrations, recording each in `migration_log`.
3. Creates the admin user `admin` / `admin` (email `admin@localhost`) and the `Main Org.` organization because the user table is empty.
4. Requires login: anonymous access, sign-up, LDAP and auth proxy are off. The well-known default password is the main security exposure.
5. Loads 54 built-in plugins (core data sources compiled into the binary, frontends from `public/app/plugins/`), finds no external plugins, then downloads `grafana-lokiexplore-app` from grafana.com into `data/plugins/` in the background.
6. Leaves SMTP, the image renderer, Redis/Memcached caching and external auth inactive because none of them is configured.
7. Depends on the generated `pkg/server/wire_gen.go` and the built frontend.

On every later start the existing `data/` state is reused: migrations are all skipped (`performed=0 skipped=626`), admin creation is bypassed because a user exists, the downloaded plugin is loaded from disk (55 plugins), and startup is faster.
