I started by examining the SimpleLogin codebase to understand how inbound email replies are resolved to contacts, focusing on the `handle_reply()` function and the `reply_email` lookup mechanism. My goal is to trace the actual runtime values involved in reply resolution, observe how contacts are looked up, and determine whether race conditions or uniqueness assumptions could cause replies to be routed to the wrong user.

def handle_reply(envelope, msg: Message, rcpt_to: str) -> (bool, str):
    """
    Return whether an email has been delivered and
    the smtp status ("250 Message accepted", "550 Non-existent email address", etc)
    """

    reply_email = rcpt_to

    reply_domain = get_email_domain_part(reply_email)

    # reply_email must end with EMAIL_DOMAIN or a domain that can be used as reverse alias domain
    if not reply_email.endswith(EMAIL_DOMAIN):
        sl_domain: SLDomain = SLDomain.get_by(domain=reply_domain)
        if sl_domain is None:
            LOG.w(f"Reply email {reply_email} has wrong domain")
            return False, status.E501

    # handle case where reply email is generated with non-allowed char
    reply_email = normalize_reply_email(reply_email)

    contact = Contact.get_by(reply_email=reply_email)
    if not contact:
        LOG.w(f"No contact with {reply_email} as reverse alias")
        return False, status.E502
    if not contact.user.is_active():
        LOG.w(f"User {contact.user} has been soft deleted")
        return False, status.E502

    alias = contact.alias
    alias_address: str = contact.alias.email
```

The `get_by()` method uses `.first()` which returns only the first matching record. If multiple contacts share the same `reply_email`, only one is returned and the others are silently ignored. This is the justification for why only one contact is returned when duplicates exist.

def generate_reply_email(contact_email: str, alias: Alias) -> str:
    """
    generate a reply_email (aka reverse-alias), make sure it isn't used by any contact
    """
    # shorten email to avoid exceeding the 64 characters
    # from https://tools.ietf.org/html/rfc5321#section-4.5.3
    # "The maximum total length of a user name or other local-part is 64
    #    octets."

    include_sender_in_reverse_alias = False

    user = alias.user
    # user has set this option explicitly
    if user.include_sender_in_reverse_alias is not None:
        include_sender_in_reverse_alias = user.include_sender_in_reverse_alias

    if include_sender_in_reverse_alias and contact_email:
        # make sure contact_email can be ascii-encoded
        contact_email = convert_to_id(contact_email)
        contact_email = sanitize_email(contact_email)
        contact_email = contact_email[:45]
        # use _ instead of . to avoid AC_FROM_MANY_DOTS SpamAssassin rule
        contact_email = contact_email.replace("@", "_at_")
        contact_email = contact_email.replace(".", "_")
        contact_email = convert_to_alphanumeric(contact_email)

    reply_domain = config.EMAIL_DOMAIN
    alias_domain = get_email_domain_part(alias.email)
    sl_domain = SLDomain.get_by(domain=alias_domain)
    if sl_domain and sl_domain.use_as_reverse_alias:
        reply_domain = alias_domain

    # not use while to avoid infinite loop
    for _ in range(1000):
        if include_sender_in_reverse_alias and contact_email:
            random_length = random.randint(5, 10)
            reply_email = (
                # do not use the ra+ anymore
                # f"ra+{contact_email}+{random_string(random_length)}@{config.EMAIL_DOMAIN}"
                f"{contact_email}_{random_string(random_length)}@{reply_domain}"
            )
        else:
            random_length = random.randint(20, 50)
            # do not use the ra+ anymore
            # reply_email = f"ra+{random_string(random_length)}@{config.EMAIL_DOMAIN}"
            reply_email = f"{random_string(random_length)}@{reply_domain}"

        if available_sl_email(reply_email):
            return reply_email

    raise Exception("Cannot generate reply email")


```

This shows the check-then-use pattern. At line 1150, the function checks `available_sl_email(reply_email)` and if True, returns the email for later use. But no lock or atomic operation ensures the email remains available between the check and the eventual database insert.

The `available_sl_email()` function:

```
sed -n '1425,1433p' /app/app/models.py
```

Output:

```
def available_sl_email(email: str) -> bool:
    if (
        Alias.get_by(email=email)
        or Contact.get_by(reply_email=email)
        or DeletedAlias.get_by(email=email)
    ):
        return False
    return True

```

This function performs a simple database read without acquiring any lock. Concurrent processes can both observe the email as "available" before either has written their contact record, leading to duplicate `reply_email` values.

So `user = alias.user` and the `EmailLog` (`user_id=contact.user_id`, `alias_id=contact.alias_id`) both come from whichever contact `Contact.get_by()` returned. The sender's mailbox is only checked against that contact's alias: if it does not match, the alias owner of the resolved contact is notified (E214); if that alias has `disable_email_spoofing_check` on, the reply is sent through it.

The observation script has three roles. `setup` creates two users with one alias each. `forward` sends one inbound email from newsletter@shop.example to a user's alias through `email_handler.handle()`, so the contact and its reverse alias are created by the normal forward path (`get_or_create_contact()` -> `create_contact()` -> `generate_reply_email()`). Two `forward` processes run at the same time. To make both processes draw the same reverse-alias candidate deterministically, the script pins `random_string()` to one value, and it holds each process right after its `available_sl_email()` check until the other process has also checked, which is the window between the check and `Contact.create()`. `replies` then sends replies to the reverse alias through `email_handler.handle()`, prints every `Contact.get_by(reply_email=...)` call made inside `handle_reply()` with a timestamp, and prints the resulting SMTP status, the reply `EmailLog` rows and the emails SimpleLogin produced (captured with `mail_sender.store_emails_instead_of_sending()` instead of sending them).

These runtime values show the whole failure:

- Two contact records share `reply_email=newsletter_at_shop_example_kqzvtrwmhxbnpdlsyfgjcaeuoi@sl.local`: Contact id=1 (user_id=2, bob, alias_id=4) and Contact id=2 (user_id=1, alice, alias_id=2). `Contact.filter_by(reply_email=...).count()` is 2, but `Contact.get_by(reply_email=...)` returns exactly one object, Contact id=1, user_id=2.
- The extracted reply email (the RCPT TO address) is identical in reply events 1, 2 and 3, and every lookup inside `handle_reply()` resolved it to the same Contact id=1, user_id=2, alias_id=4, at 22:05:54.150, 22:05:54.693 and 22:05:55.232. Alice's own contact (id=2) was never returned, so the lookup is stable but always picks bob's row.
- Reply event 1: alice (user_id=1), the owner of alias_id=2 and of Contact id=2, replied to her reverse alias. It resolved to Contact id=1, user_id=2, so the forwarding user and alias became bob's (user_id=2, alias_id=4). Her mailbox is not a mailbox of alias 4, so the reply was not sent to the contact. Instead SimpleLogin sent bob@mailbox.test (user_id=2) the alert "Attempt to use your alias word_test000@sl.local from alice@mailbox.test" and returned `250 SL E214 Unauthorized for using reverse alias`. Alice's reply was handled for, and delivered as an alert to, a different user than the owner of her alias.
- Reply event 2: bob replied to the same address. It resolved to his own contact and was sent normally (`EmailLog id=3: user_id=2, alias_id=4, contact_id=1, mailbox_id=2`, From word_test000@sl.local). For bob the delivery is correct, which is why the problem does not show up for the user whose row happens to come first.
- Reply event 3: after bob turned on `disable_email_spoofing_check` for alias 4, alice's reply was forwarded. It was logged as `EmailLog id=4: user_id=2, alias_id=4, contact_id=1, mailbox_id=2` and sent to newsletter@shop.example From bob's alias word_test000@sl.local. Alice's reply (alias owner user_id=1) was forwarded under user_id=2 through bob's alias and mailbox.
- Reply event 4: for ra+nonexistentxyz@sl.local, `Contact.get_by()` inside `handle_reply()` returned None. SimpleLogin logged "No contact with ra+nonexistentxyz@sl.local as reverse alias" and returned `550 SL E502 Email not exist`, so the reply is rejected with a 550 and the sending server bounces it back to the sender. A duplicate does not produce this temporary failure: as long as at least one contact has the reply email, the lookup always succeeds, it just returns the wrong one.

The root cause is the combination of three things in the code shown above:

1. `generate_reply_email()` checks `available_sl_email()` and returns the address, and `create_contact()` inserts it later without a lock or retry. Two concurrent contact creations can both pass the check (shown above by the two processes at 22:05:51.740).
2. `reply_email` has only a non-unique index (`index=True` at line 1899 of `app/models.py`, `unique=False` in the migration), and the only unique constraint is `(alias_id, website_email)`, so both inserts succeed with no IntegrityError.
3. `handle_reply()` resolves the contact with `Contact.get_by(reply_email=reply_email)`, which is `.first()` without ordering, and then takes the alias, the user and the `EmailLog` owner from that one contact. Every reply to the shared address is attributed to the same contact (here id=1, user_id=2), so the other user's replies are routed to the wrong user: rejected with an alert sent to the other alias owner, or forwarded through the other user's alias when its spoofing check is disabled.

The routing error comes from the duplicate `reply_email` value and the single-row lookup, not from how the email is parsed: the RCPT TO value and the normalized reply email were the same correct address in every event.
