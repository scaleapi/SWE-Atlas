I first started the broker (Redis) and verified it was reachable, because Paperless uses Redis for `django-q` background tasks and for Django Channels (websocket status updates) at runtime.

```bash
W=/tmp/paperless-ngx-idle-test
```

This shows what keeps running while the system is idle and how often:

- The four schedules created by the migrations: "Check all e-mail accounts" (`paperless_mail.tasks.process_mail_accounts`, schedule type I = every 10 minutes), "Train the classifier" (`documents.tasks.train_classifier`, H = hourly), "Optimize the index" (`documents.tasks.index_optimize`, D = daily) and "Perform sanity check" (`documents.tasks.sanity_check`, W = weekly). Each `next_run` is exactly one interval after the previous run time.
- The qcluster scheduler checks for due schedules every 30 seconds; its first check, 30 s after start (01:22:28), found all four schedules due and created and processed one task for each. The sanity check logged "Sanity checker detected no issues.", a concrete runtime health signal. The mail check ran again at 01:31:59, ten minutes later, and is the entry that repeats most often while idle.
- After each task django-q logs "recycled worker" and a fresh "Process-1:N ready for work at <pid>" line, so the worker pool returns to the ready state after every scheduled run.
- The consumer logged nothing after "Using inotify to watch directory for changes" for the whole idle period: zero documents were ingested while the scheduled tasks ran.

To observe runtime behavior during a short broker outage, I stopped Redis while the system was otherwise idle. During the outage the consumer detected a new file and tried to enqueue it, then logged a Redis connection failure; after Redis came back, the consumer enqueued a new file successfully. `qcluster` logged broker connection errors during the outage, including a django-q logging-formatting error ("--- Logging error ---") when its pusher process lost the connection.

```bash
kill $(cat $W/run/redis.pid); sleep 1
redis-cli ping || true

printf 'hello during redis outage\n' > $W/consume/outage_test.txt
sleep 2
```

So the components that keep running continuously to maintain Paperless-NGX in a ready state, even when no documents are being processed, are: Redis (the django-q broker and channels layer); the `qcluster` process, which runs the guard, monitor, pusher and worker processes and the scheduler loop that creates tasks from the four schedules; the `document_consumer` process blocked on inotify events for the consumption directory; and the Gunicorn webserver with its workers serving the UI and API.

After completing the runtime observation (idle activity, periodic schedules, ready indicators, and restart/reconnect behavior), I stopped all started processes and removed the isolated `/tmp` workspace, which held the SQLite database, the media files and all logs.
