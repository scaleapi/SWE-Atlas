$ Xvfb :99 -screen 0 1024x768x24 &
$ export DISPLAY=:99
$ cd /app && python3 setup.py build --verbose 2>&1 | tail -5

This output reveals the complete input decision process. The Press event shows GLFW receiving the X11 keycode (0x26), translating it via XKB to the symbol 'a', and invoking the C-level on_key_input handler. The handler determines this is a text key and sends it to the child process; Return has no text, so it is sent as an encoded key (0xd). Every Release event reaches on_key_input with empty text and is ignored, because the current keyboard mode does not support encoding this event.

The main thread's loop is glfwRunMainLoop in glfw-x11.so, called from main_loop in fast_data_types.so; the Python interpreter frames sit underneath it as the caller that started the loop. The ChildMonitor thread waits in poll() inside io_loop, the C function that performs the pty write.

This confirms the complete path: GLFW callback (C) → on_key_input in keys.c (C) → schedule_write_to_child queues data and wakes the I/O thread → ChildMonitor thread writes to pty.

Examining the source code confirms this architecture. In keys.c, the on_key_input function is called from the GLFW key callback:

// From kitty/keys.c (lines 166-182)
void
on_key_input(GLFWkeyevent *ev) {
    Window *w = active_window();
    const int action = ev->action, mods = ev->mods;
    const uint32_t key = ev->key, native_key = ev->native_key;
    const char *text = ev->text ? ev->text : "";
    ...
    if (!w) { debug("no active window, ignoring\n"); return; }
    ...
}

The active_window() function in keys.c determines which window receives input:

// From kitty/keys.c (lines 106-111)
static Window*
active_window(void) {
    Tab *t = global_state.callback_os_window->tabs + global_state.callback_os_window->active_tab;
    Window *w = t->windows + t->active_window;
    if (w->render_data.screen) return w;
    return NULL;
}

This shows the focus hierarchy: the global_state tracks the current OS window, which contains tabs, and each tab has an active_window index. The input is routed to tabs[active_tab].windows[active_window].

Focus changes are propagated through GLFW's window_focus_callback in glfw.c:

// From kitty/glfw.c (lines 514-517)
static void
window_focus_callback(GLFWwindow *w, int focused) {
    if (!set_callback_window(w)) return;
    debug_input("\x1b[35mon_focus_change\x1b[m: window id: 0x%llu focused: %d\n", ...);

When a window loses focus or is closed, any pending input is simply discarded. The on_key_input function checks active_window() at line 182, and if it returns NULL (no active window or window closed), the input is ignored with the debug message "no active window, ignoring". I observed this behavior directly in the runtime debug output: after enabling key debugging and sending a keystroke to a window with no active child, the log showed the key event arriving at on_key_input and then being dropped:

```
[31.204] on_key_input: glfw key: 0x7a (z) scancode: 0x2c action: PRESS mods: 0 text: 'z' state: 0
no active window, ignoring
```

This captured runtime output confirms there is no queuing of input for unfocused windows; the key reaches on_key_input but is immediately discarded because active_window() returned NULL.

From the runtime artifacts, I can infer the Python/C/GLFW boundaries:

1. GLFW (external library): Handles X11/Wayland communication, receives raw key events via XKB, manages window focus. This is evident from the "xkb_keycode" in debug output and from the main thread (TID 699) reading the X11 connection on fd 3 (socket:[364] in the fd listing) with recvmsg(3, ...), as in the 16:56:47.497429 step below.

2. C layer (kitty/keys.c, kitty/child-monitor.c): The on_key_input function processes keys, encodes them, and schedules writes via schedule_write_to_child. The ChildMonitor runs in a separate thread and performs actual writes to the pty.

3. Python layer (kitty/main.py, kitty/boss.py): The main event loop is started from Python (_run_app calls into main_loop in C), and shortcut handling goes through Python (dispatch_possible_special_key is called via PyObject_CallMethod in keys.c).

I can rule out two plausible but incorrect interpretations:

First incorrect interpretation: "Python handles the primary input dispatch." The strace timing evidence disproves this. I traced one more keypress with `strace -f -tt -T -p $KITTY_PID -e trace=write,read,recvmsg,recvfrom,poll,ppoll,futex -s 40 -o /tmp/st_full.txt` while running `xdotool key z`. The steps arrive in this order:
- 16:56:47.497429 thread 699 reads the key event from the X11 socket (recvmsg on fd 3)
- 16:56:47.497981 thread 699 logs GLFW's XKB translation ("Press xkb_keycode: 0x34 ... z")
- 16:56:47.498883 thread 699 logs on_key_input (C, keys.c)
- 16:56:47.500096 thread 699 writes fd 7, waking the ChildMonitor
- 16:56:47.500821 thread 711 writes "z" to fd 10, the pty

The whole path from the X event to the pty write takes 3.4 ms and runs on two native threads. The thread list has no Python worker thread, and the gdb snapshot shows the main thread's event loop is GLFW's C loop, with Python only below it as the caller that started it. Python does run on the main thread during a key press: on_key_input calls boss.dispatch_possible_special_key to check for shortcuts, inside the 1.2 ms between the on_key_input line and the fd 7 wakeup. But the event is received and translated before that, and the pty write comes after it on the C ChildMonitor thread. Normal text keys reach the child through C; Python only gets a chance to consume a key as a shortcut.

Second incorrect interpretation: "GLFW directly writes to the child pty." The multi-thread strace proves this wrong. GLFW runs in the main thread (TID 699): every X11 socket read happens there. Every write to the pty fd 10 comes from TID 711 (KittyChildMon), always after the main thread's fd 7 wakeup. In a burst (`xdotool type --delay 0 'hello world'` under `strace -f -tt`), all 11 characters followed this pattern: 11 separate one-byte writes to fd 10 from TID 711, each 174–424 µs after its wakeup. GLFW only delivers the key event; it has no knowledge of child processes or ptys. The C code in kitty acts as the bridge, queuing data and signaling the ChildMonitor thread.

Regarding correctness-versus-responsiveness tradeoffs, I observed mutex locking in the write path. Looking at child-monitor.c:

// From kitty/child-monitor.c (lines 74-79, 336-365)
#define screen_mutex(op, which) \
    pthread_mutex_##op(&screen->which##_buf_lock);

// In schedule_write_to_child:
screen_mutex(lock, write);
... memcpy to write_buf ...
if (screen->write_buf_used) wakeup_io_loop(self, false);
screen_mutex(unlock, write);

This locking mechanism is a synchronous correctness guarantee at the cost of responsiveness. The main thread takes the children lock and the write_buf_lock mutex, adds the data to the buffer, wakes the ChildMonitor and only then releases the locks. The ChildMonitor thread must acquire the locks before it can drain the buffer.

The burst trace shows this lock at work. For "o", the ChildMonitor woke while the main thread still held the children lock and blocked on it (the futex address 0x2b3bdb21f6c0 is in fast_data_types.so's static data, next to children_fds in the gdb output):

711   16:56:53.548985 futex(0x2b3bdb21f6c0, FUTEX_WAIT_PRIVATE, 2, NULL <unfinished ...>
699   16:56:53.549014 <... write resumed>) = 8
699   16:56:53.549064 futex(0x2b3bdb21f6c0, FUTEX_WAKE_PRIVATE, 1) = 1
699   16:56:53.549114 write(2, "sent key as text to child: o\n", 29 <unfinished ...>
711   16:56:53.549145 <... futex resumed>) = 0
699   16:56:53.549171 <... write resumed>) = 29
711   16:56:53.549194 futex(0x2b3bdb21f6c0, FUTEX_WAKE_PRIVATE, 1) = 0
699   16:56:53.549240 write(4, "\1\0\0\0\0\0\0\0", 8) = 8
711   16:56:53.549321 write(10, "o", 1 <unfinished ...>

Thread 711 waited 160 µs (16:56:53.548985 → .549145) until the main thread released the lock, then wrote "o". For "r" the same lock was contended briefly (FUTEX_WAIT returned EAGAIN at .558127) before the write at .558305. The tradeoff: the main thread never waits on a slow pty write and goes back to reading X events, and the locked, shared buffer keeps every byte in order (h-e-l-l-o- -w-o-r-l-d reached fd 10 in exactly the order the keys were queued). The cost is a cross-thread handoff of a few hundred microseconds per key (174–424 µs in the burst, 208 µs for "y", 725 µs for "z"), plus occasional lock waits. The same lock can make the main thread wait while the ChildMonitor holds it during a write to the pty. An alternative lock-free design using a lock-free queue would trade correctness guarantees (like memory ordering) for potentially better responsiveness under contention, but Kitty chose the mutex approach for predictable behavior.

Additionally, there's a buffer size tradeoff visible in the code: the write buffer can grow up to 100MB before input is discarded ("Too much data being sent to child...ignoring it"). This queuing behavior prioritizes eventual delivery over immediate backpressure, which improves responsiveness for burst input but could delay feedback if the child is slow.
